# 1. Mission

## 1.1 Канонічна місія

**AIRA — це мікроядерна федеративна система координованого зменшення невизначеності, яка перетворює Problem Statement користувача на Verified Result Artifact з мінімальною сукупною вартістю шляхом повторного використання готових рішень, перевірених знань і мінімально достатньої композиції доступних можливостей.**

## 1.2 Заборонені тлумачення

AIRA не є:

```text
GPU marketplace
LLM runtime
cloud inference platform
blockchain compute market
centralized AI service
```

Ці моделі були ранніми етапами еволюції, але перекриті канонічною формулою. Початковий документ описував P2P LLM/GPU compute network, але пізніша модель перейшла до Problem Statement → Progressive Resolution → Verified Result Artifact.

# 2. First Principles

## A0. Reality Primacy

AIRA не створює істину.

AIRA:

```text
збирає Evidence;
зменшує невизначеність;
формує епістемічно обґрунтовані артефакти;
явно показує альтернативи, якщо однозначного вибору немає.
```

## A1. Problem Primacy

Будь-яка робота системи починається з:

```text
Problem Statement
```

Не з моделі, не з GPU, не з маршруту, не з Execution.

## A2. Context Primacy

Перед будь-яким Resolution має бути Context.

Без Context система не має права інтерпретувати Problem Statement.

## A3. Reuse Before Compute

AIRA завжди перевіряє:

```text
готове рішення
↓
перевірене знання
↓
дешеве джерело інформації
↓
легке виконання
↓
важке виконання
↓
розподілене виконання
↓
дослідницька ескалація
```

Обчислення є останнім засобом.

## A4. Minimal Necessary Action

Система переходить до дорожчого методу тільки після того, як дешевший метод у межах свого контракту не досяг Success Criterion.

## A5. Evidence Primacy

Knowledge не є джерелом істини.

```text
Evidence → Epistemic Processing → Operational Knowledge
```

Знання не мають TTL. Вони мають статус, довіру, область застосування, докази й контрдокази.  

## A6. Human Final Collapse

Якщо після об'єктивної редукції залишаються кілька епістемічно рівноправних областей рішень, остаточний вибір виконує людина.

AIRA не має права приховано обирати між рівноправними нормативними альтернативами.

## A7. Evolution Separation

Operational Plane і Evolution Plane ізольовані.

Evolution Plane не змінює Operational Plane напряму. Нові знання, гіпотези, евристики або артефакти проходять:

```text
Evidence
↓
Validation
↓
Artifact Promotion
↓
Operational Use
```

# 4. Canonical Pipeline

## 4.1 Operational Pipeline

```text
Problem Statement
↓
Interpret
↓
Reduce
↓
Differentiate
↓
Organize
↓
Materialize
↓
Verify
↓
Verified Result Artifact
```

## 4.2 Опис операторів

```text
Interpret      — визначає Context.
Reduce         — звужує Solution Space.
Differentiate  — розділяє рівноправні області рішень.
Organize       — формує структуру виконання.
Materialize    — виконує необхідну роботу.
Verify         — перетворює Output на Verified Result Artifact.
```

`Differentiate` потрібен для етичних, нормативних, стратегічних і відкритих задач, де поле рішень не звужується до однієї області, а розщеплюється.

## 4.3 Evolution Pipeline

```text
Evidence
↓
Aggregate
↓
Discover
↓
Validate
↓
Promote
↓
Operational Artifact
```

Evolution Plane працює у фоні й не блокує Operational Plane.

```text
Verified Result Artifact
Ready Solution Artifact
Knowledge Artifact
Evidence Artifact
Best Current Hypothesis Artifact
Negative Result Artifact
Open Research Artifact
Operational Artifact
Research Artifact
```

## 5.1 Головне правило

Кожне завершення роботи AIRA породжує Artifact.

Навіть якщо рішення не знайдено, система повинна створити:

```text
Negative Result Artifact
```

або

```text
Open Research Artifact
```

Тобто виконання не завершується "нічим".

# 7. Solution Space Model

## 7.1 Основна модель

Problem Statement породжує не рішення, а:

```text
Solution Space
```

AIRA поступово звужує або диференціює цей простір.

## 7.2 Solution Uncertainty

Solution Uncertainty — внутрішня математична міра невизначеності щодо вибору найкращого способу отримання Verified Result Artifact.

Вона не є місією AIRA.

Правильна ієрархія:

```text
Mission:
    отримати Verified Result Artifact

Optimization Objective:
    мінімізувати сукупну вартість

Mathematical Mechanism:
    Progressive Reduction of Solution Uncertainty
```

# 8. Cost Model

## 8.1 Total Cost

Сукупна вартість включає:

```text
Compute
Energy
Latency
Network
Storage
Information
Risk
Verification
Future Cost
```

## 8.2 CSU KPI

Канонічна метрика CSU:

```text
Expected Evidence Gain / Total Acquisition Cost
```

або в загальній формі:

```text
ΔSolution Uncertainty / Total Cost
```

CSU не повинен збирати інформацію "про всяк випадок".

# 9. Escalation Model

## 9.1 Рівні ескалації

```text
L0 Ready Solution
L1 Verified Knowledge
L2 Deterministic Resolution
L3 Exploratory Resolution
L4 Cognitive Evolution
```

## 9.2 Критерій ескалації

Ескалація дозволена лише якщо:

```text
нижчий рівень виконав свій контракт;
Success Criterion не досягнуто;
Budget або Evidence Gain не виправдовують продовження;
залишкова невизначеність перевищує поріг.
```

## 9.3 Відкриті задачі

Якщо Verified Result Artifact неможливий, допустимі результати:

```text
Best Current Hypothesis Artifact
Negative Result Artifact
Open Research Artifact
```

# 10. Operational / Evolution Separation

## 10.1 Operational Plane

Відповідає за:

```text
Problem Statement → Verified Result Artifact
```

## 10.2 Evolution Plane

Відповідає за:

```text
Evidence → Artifact Promotion → дешевше майбутнє вирішення
```

## 10.3 Заборона

Background/Evolution Plane не може напряму створити Operational Artifact.

Тільки через:

```text
Evidence
↓
Epistemic Validation
↓
Artifact Promotion
```

# 11. Core Architecture Boundary

Book 0 фіксує межу Core.

Kernel не містить:

```text
AI
ML
HIE
Scheduler
Blockchain
GPU logic
LLM logic
Optimization algorithms
Knowledge algorithms
```

Kernel містить лише:

```text
Object Model
ABI
Event Runtime
Policy Gate
Invariant Checker
Security Boundary
```

Це узгоджується з Microkernel Architecture, Stable ABI і Lightweight Architecture Doctrine.   

---

# 12. Architecture Freeze Rule

Після Book 0 v0.1:

```text
нові фундаментальні сутності не додаються;
нові можливості реалізуються через CSU / Protocol / Algorithm / Artifact;
нові ідеї спочатку потрапляють до Research Track;
Core змінюється лише при доведеній неповноті або суперечності.
```
